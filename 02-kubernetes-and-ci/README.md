## 1. Kubernetes가 실행하는 이미지부터 확인한다

컨테이너 이미지는 애플리케이션 코드, 외부 라이브러리, 런타임과 운영체제 구성요소를 함께 담습니다. 이미지가 변조되거나 취약하면 Kubernetes도 해당 프로그램을 그대로 실행할 수 있습니다.

공급망 관점에서는 다음 항목을 확인해야 합니다.

- 신뢰할 수 있는 Registry에서 가져오는가?
- 변경 가능한 태그 대신 `sha256` digest로 고정했는가?
- 이미지 서명과 출처를 검증하는가?
- 빌드·배포·운영 단계에서 알려진 취약점을 검사하는가?
- 운영 이미지에 셸과 디버깅 도구 같은 불필요한 파일이 들어 있지 않은가?
- 컨테이너가 root가 아닌 사용자로 실행되는가?

digest는 특정 이미지 내용을 고정하지만 그 이미지가 안전하다는 의미는 아닙니다. 신뢰할 수 있는 주체가 만든 이미지인지 확인하려면 서명과 provenance 검증을 함께 사용해야 합니다.

## 2. imagePullSecret은 Registry의 열쇠다

Private Registry에서 이미지를 받으려면 인증정보가 필요합니다. Kubernetes의 `imagePullSecret`은 Registry 아이디·비밀번호 또는 토큰을 보관하고, kubelet은 이를 사용해 Pod에 필요한 이미지를 가져옵니다.

Secret의 `data` 값은 Base64로 표현될 뿐 암호화된 것이 아닙니다. 또한 별도 설정이 없다면 Secret은 etcd에 암호화되지 않은 상태로 저장됩니다.

따라서 두 가지 권한을 함께 최소화해야 합니다.

1. Kubernetes에서 누가 Secret을 읽거나 Pod를 생성할 수 있는지 제한
2. Secret 안의 Registry 계정에는 필요한 이미지 다운로드 권한만 부여

## 3. Kubernetes API 요청은 여러 보안 관문을 통과한다

CI/CD가 Deployment를 수정하면 요청은 다음 단계를 거칩니다.

```text
TLS 연결
→ 인증(Authentication)
→ 인가(Authorization)
→ Admission Control
→ API 유효성 검사
→ etcd에 원하는 상태 저장
```

- **TLS:** 통신 내용을 암호화하고 올바른 API Server와 연결되었는지 확인
- **인증:** 요청한 사용자 또는 ServiceAccount의 신원 확인
- **인가:** 해당 주체가 특정 리소스에 특정 작업을 수행할 권한이 있는지 확인
- **Admission:** 생성·변경하려는 오브젝트의 실제 내용이 설정된 정책을 만족하는지 확인
- **유효성 검사:** 요청 형식과 값이 Kubernetes API 규격에 맞는지 확인

## 4. RBAC과 Admission은 서로 다른 질문에 답한다

RBAC은 다음을 판단합니다.

> 이 계정이 이 네임스페이스의 Deployment를 수정해도 되는가?

Admission은 다음을 판단합니다.

> 이 계정이 제출한 Deployment의 이미지와 보안 설정을 허용해도 되는가?

배포 권한이 있는 CI/CD 계정이라도 Admission 정책을 이용하면 다음과 같은 요청을 거부할 수 있습니다.

- 허용되지 않은 Registry의 이미지
- `latest` 태그 또는 digest가 없는 이미지
- 서명이 검증되지 않은 이미지
- privileged 컨테이너
- root 사용자로 실행되는 컨테이너

이 항목들은 Kubernetes가 모두 기본으로 차단하는 것이 아닙니다. Pod Security Admission, ValidatingAdmissionPolicy, Admission Webhook 또는 별도의 정책 도구를 관리자가 설정해야 합니다.

## 5. 토큰이 탈취돼도 마지막 단계에서 차단한다

공격자가 CI/CD 토큰을 훔치면 정상 CI/CD 계정처럼 보여 인증을 통과할 수 있습니다. 계정에 배포 권한이 있다면 인가도 통과할 수 있습니다.

하지만 이미지 서명 검증 정책이 구성되어 있다면 Admission 단계에서 서명되지 않았거나 승인되지 않은 악성 이미지를 거부할 수 있습니다.

```text
탈취한 CI/CD 토큰으로 배포 요청
→ 인증 통과 가능
→ 인가 통과 가능
→ Admission에서 이미지 출처·digest·서명 검사
→ 정책 위반 이미지 배포 차단
```

하나의 장치에만 의존하지 않고 TLS, 토큰 보호, 최소 권한 RBAC, Admission 이미지 정책과 감사 로그를 함께 사용해야 합니다.

## 6. etcd에 저장된 원하는 상태가 실제 실행으로 이어진다

모든 검사를 통과한 오브젝트는 etcd에 저장됩니다. 이후 Controller, Scheduler와 kubelet이 원하는 상태를 실제 상태로 만듭니다.

```text
원하는 상태를 etcd에 저장
→ Controller가 필요한 오브젝트 생성
→ Scheduler가 실행할 노드 결정
→ kubelet이 컨테이너 실행
```

etcd를 여러 멤버로 구성하는 이유는 데이터를 각각 따로 관리하기 위해서가 아니라, 합의를 통해 상태를 복제하고 일부 멤버에 장애가 발생해도 클러스터를 유지하기 위해서입니다.

## 7. 감사 로그는 클러스터의 CCTV다

감사(Audit)는 요청을 직접 차단하지 않고 다음과 같은 내용을 기록합니다.

- 누가 요청했는가?
- 언제, 어디에서 요청했는가?
- 어떤 네임스페이스와 리소스를 변경했는가?
- 요청이 허용됐는가, 거부됐는가?

감사 로그는 이상행위 탐지, 사고 원인 분석과 피해 범위 조사에 사용됩니다. 자동 탐지가 필요하면 감사 로그를 SIEM이나 모니터링 시스템으로 보내 탐지 규칙을 구성해야 합니다.

## 8. Slopsquatting: LLM의 패키지 환각을 악용한다

Slopsquatting은 LLM이 존재하지 않는 패키지를 추천하고, 공격자가 그 이름으로 악성 패키지를 먼저 등록해 설치를 유도하는 공급망 공격입니다.

```text
개발자가 LLM에 코드 생성 요청
→ LLM이 존재하지 않는 패키지 추천
→ 공격자가 같은 이름으로 npm·PyPI에 악성 패키지 등록
→ 다른 개발자나 코딩 에이전트가 설치
→ 설치 또는 실행 과정에서 악성코드 실행 가능
```

패키지가 Registry에 존재한다는 사실만으로 안전하다고 판단하면 안 됩니다. 최초 등록일, 관리자, 소스 저장소, 설치 스크립트, 다운로드 기록과 조직의 승인 여부를 함께 확인해야 합니다.

## 이번 자료에서 기억할 핵심

1. Kubernetes는 이미지가 악성인지 자동으로 판단하지 않는다.
2. digest는 이미지 내용을 고정하지만 신뢰성과 안전성을 보장하지 않는다.
3. Secret 접근 권한과 Registry 계정 권한을 모두 최소화해야 한다.
4. 인증은 신원을 확인하고, RBAC은 행동 범위를 제한한다.
5. Admission은 사전에 설정한 정책으로 위험한 배포 내용을 검사한다.
6. 감사 로그는 차단 기능이 아니라 탐지와 사고 조사를 위한 기록이다.
7. LLM이 추천한 패키지도 설치 전에 출처와 신뢰성을 확인해야 한다.
