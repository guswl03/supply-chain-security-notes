# 국내 쿠버네티스 보안시장의 빈틈

## 핵심 문제의식

글로벌 클라우드 보안제품은 기능이 풍부하지만 국내 금융·공공·제조 환경에 그대로 적용하기 어려울 수 있다. 이 자료는 그 이유를 다음 세 가지 시장 가설로 정리한다.

1. 폐쇄망과 온프레미스 지원의 어려움
2. 국내 규제·컴플라이언스와 기술 통제의 연결 부족
3. CI부터 CD까지 이어지는 통합 보안정책 적용의 어려움

여기서 ‘국내에 제품이 없다’는 표현은 확정된 사실이 아니라 경쟁사 조사와 고객 인터뷰로 검증해야 하는 가설이다.

## 1. 폐쇄망과 온프레미스

### 충돌하는 운영 방식

많은 SaaS 보안제품은 외부 서비스와 지속적으로 통신하면서 정책, 취약점 데이터베이스, 위협정보와 업데이트를 받는다. 반면 망분리·폐쇄망 환경은 외부 연결을 제한하거나 차단한다.

```text
SaaS 보안제품
외부 API·클라우드·실시간 업데이트 필요
                 ↕ 충돌
폐쇄망 조직
외부 연결 제한·내부 설치·반입 절차 필요
```

이 차이 때문에 다음 문제가 생길 수 있다.

- SaaS 콘솔로 텔레메트리를 전송하기 어려움
- 컨테이너 이미지와 소스코드를 외부 서비스에서 검사하기 어려움
- CVE 데이터베이스와 탐지 규칙을 실시간 갱신하기 어려움
- 라이선스 인증이나 원격 관리 기능이 동작하지 않을 수 있음
- 업데이트 파일을 검토하고 내부망에 반입하는 별도 절차가 필요함

### 제품이 제공해야 할 기능

- 인터넷 없이 설치·운영 가능한 온프레미스 구성
- 취약점 DB, 정책과 소프트웨어 패키지의 오프라인 번들
- 업데이트 파일의 서명 및 무결성 검증
- 내부 미러·프록시를 통한 단계적 업데이트
- 외부로 나가는 데이터가 없는 로컬 분석
- 망 구간별 승인, 반입과 변경 이력 기록

폐쇄망 지원은 단순히 설치파일을 제공하는 문제가 아니다. 업데이트 공급망 자체의 출처, 서명, 승인과 롤백까지 설계해야 한다.

## 2. 국내 컴플라이언스 매핑

글로벌 도구는 CIS Benchmark, NIST 등 국제 기준을 중심으로 결과를 보여주는 경우가 많다. 국내 조직은 이 결과를 ISMS-P, CSAP, 전자금융 관련 요구사항 및 내부 보안기준과 연결해서 설명해야 한다.

```text
기술 검사 결과
예: privileged 컨테이너 발견
        ↓
보안 통제
예: 권한 상승 제한·최소 권한
        ↓
규정 및 내부 기준
        ↓
감사 증빙과 조치 이력
```

필요한 것은 단순한 ‘통과/실패’ 보고서가 아니다.

- 각 기술 검사 항목과 규정 통제항목의 매핑
- 적용 대상과 예외 사유의 기록
- 발견, 담당자 지정, 조치, 재검증까지의 이력
- 특정 시점의 정책 버전과 검사 결과 재현
- 경영진, 보안팀, 개발팀, 감사자가 이해할 수 있는 서로 다른 보고서

주의할 점은 기술 정책 하나가 규정 준수를 완전히 증명하지는 못한다는 것이다. 조직·절차·물리적 통제와 결합해야 하며, 법률·규제 해석은 담당 전문가가 검토해야 한다.

## 3. CI/CD 보안 통합의 어려움

개발과 운영 과정에는 서로 다른 팀과 도구가 참여한다.

```text
Git 저장소
  → Jenkins / GitHub Actions / GitLab CI
  → 이미지 저장소
  → Helm / GitOps / Argo CD
  → Kubernetes Admission
  → 실행 중인 워크로드
```

각 구간에 코드 분석, 시크릿 탐지, 이미지 취약점 검사, IaC 검사와 런타임 탐지 도구를 따로 붙일 수 있다. 문제는 결과와 정책이 분리되기 쉽다는 점이다.

- CI에서 승인된 산출물과 CD에서 배포되는 산출물이 같은지 확인하기 어려움
- 여러 스캐너 결과가 중복되거나 기준이 달라 최종 판정이 모호함
- 정책 문서는 존재하지만 파이프라인에서 자동으로 강제되지 않음
- 실패 이유가 개발자에게 늦게 전달되거나 이해하기 어려움
- 예외 승인과 만료 시점이 체계적으로 관리되지 않음

## 아이디어 A: CI/CD 네이티브 보안 게이트웨이

여러 검사 결과를 하나의 정책 판정으로 통합한다.

```text
코드·이미지·Manifest
       ↓
취약점 + 시크릿 + IaC + 조직 정책 검사
       ↓
Pass / Warn / Fail
       ↓
PR 피드백 · 빌드 차단 · 배포 승인
```

### 구성 후보

- Trivy 등의 도구로 이미지·의존성 취약점 검사
- gitleaks 계열 도구로 저장소의 시크릿 탐지
- Dockerfile, Helm Chart와 Kubernetes Manifest 설정 검사
- OPA 계열 정책 엔진으로 조직 규칙 판정
- PR/MR 코멘트와 대시보드로 결과 통합
- 실패 시 머지·빌드·배포를 정책에 따라 차단

### 중요한 설계 원칙

- CI에서 검사한 이미지의 digest를 CD까지 유지한다.
- 검사 결과뿐 아니라 SBOM, 서명과 provenance를 함께 연결한다.
- 차단 이유와 해결 방법을 개발자에게 명확하게 알려준다.
- 예외에는 승인자, 사유와 만료일을 반드시 둔다.
- 폐쇄망용 취약점 DB 반입 과정도 검증하고 감사한다.

단일 CLI와 GitHub Actions 같은 작은 연동으로 시작할 수 있지만, 실제 제품에서는 GitLab CI, Jenkins, Argo CD 및 사내 레지스트리까지 확장 가능성을 고려해야 한다.

## 아이디어 B: 국내 규제용 Admission 정책 팩

Kyverno나 OPA Gatekeeper 같은 검증된 엔진 위에 국내 환경에 맞는 정책 운영 계층을 제공한다.

### 정책 예시

- privileged 컨테이너 금지
- root 사용자 실행 금지
- 승인되지 않은 레지스트리 이미지 차단
- 변경 가능한 태그 대신 digest 사용 요구
- 리소스 제한과 보안 컨텍스트 요구
- 서명 또는 provenance 검증을 통과한 이미지만 허용

### 제품이 더해야 할 부분

- 규정·내부 통제항목과 정책의 매핑
- 조직별 정책 템플릿과 버전 관리
- 예외 승인·만료·재검토 워크플로
- 클러스터별 준수 현황과 변화 추적
- 감사 대응용 근거와 조치 이력 출력
- 폐쇄망 설치 및 서명된 오프라인 업데이트

Admission 정책만으로 규정 준수가 완성되지는 않는다. 배포 전에 요청을 검사하는 기술적 통제 중 하나이며, RBAC, Secret 관리, 이미지 서명, 감사로그와 사고 대응 절차가 함께 필요하다.

## 검증해야 할 시장 가설

자료의 제품 아이디어를 실제 사업 기회로 판단하려면 다음을 조사해야 한다.

1. 국내 경쟁제품이 정말 어떤 기능과 배포 방식을 제공하는가?
2. 고객은 도구 부재와 운영·인력 부족 중 무엇을 더 큰 문제로 보는가?
3. 폐쇄망 고객은 취약점 DB를 현재 어떤 주기와 절차로 반입하는가?
4. 기존 도구 통합, 규제 보고서와 정책 강제 중 어디에 비용을 지불하는가?
5. 오탐으로 배포가 중단됐을 때 누가 예외를 승인하고 책임지는가?
6. 규제가 바뀌었을 때 정책 팩과 매핑을 누가 얼마나 빨리 갱신하는가?

## 스터디 실습 제안

작게는 다음 흐름을 구현해 볼 수 있다.

1. 샘플 애플리케이션 이미지와 Kubernetes Manifest 준비
2. Trivy와 시크릿·IaC 검사 실행
3. 검사 결과를 공통 형식으로 변환
4. YAML 정책으로 Pass·Warn·Fail 판정
5. GitHub Actions에서 결과를 PR에 표시
6. 실패한 이미지의 배포 차단
7. 같은 정책을 Kyverno Admission 단계에도 적용
8. 예외 승인과 만료 이력을 기록

이 실습의 핵심은 스캐너를 새로 만드는 것이 아니라, 개발에서 배포까지 동일한 정책과 산출물 신원을 유지하는 것이다.
