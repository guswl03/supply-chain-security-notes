# 쿠버네티스 보안제품과 제품 아이디어

## 한눈에 보기

쿠버네티스 보안은 한 제품이나 기능만으로 완성되지 않는다. 일반적으로 이미지와 설정을 배포 전에 검사하고, 배포 정책을 강제하며, 실행 중 행위를 감시하고, 접근 권한과 감사 기록을 관리하는 여러 층으로 구성된다.

```text
코드·이미지 검사 → 배포 정책 검사 → 클러스터 설정 점검 → 런타임 탐지 → 접근제어·감사
```

## 보안 영역별 대표 도구

### 1. 통합 플랫폼(CNAPP·CWPP)

- Prisma Cloud: 코드와 IaC 검사, 이미지 취약점 스캔, 클라우드·쿠버네티스 설정 점검, 런타임 보호를 통합한다.
- Sysdig Secure: Falco 계열의 런타임 탐지와 컨테이너 포렌식에 강점이 있다.
- Wiz: 에이전트리스 방식으로 클라우드 구성 오류, 취약점, 권한과 노출 관계를 분석한다.
- CrowdStrike Falcon Cloud Security: 워크로드 및 런타임 보호와 이미지 보안 기능을 제공한다.
- Aqua Platform: 개발 파이프라인부터 런타임까지 컨테이너 보안을 다룬다.
- Check Point CloudGuard: 클라우드 워크로드, 네트워크 및 정책 관리 영역을 다룬다.

CNAPP와 CWPP는 제품마다 범위가 다르므로 이름만으로 기능을 단정하지 말고 실제 지원 항목과 배포 방식을 확인해야 한다.

### 2. 런타임 위협 탐지

- Falco: 리눅스 시스템 호출 등 실행 중 행위를 규칙과 비교해 이상 행동을 탐지한다.
- KubeArmor: eBPF와 리눅스 보안 기능을 이용해 프로세스, 파일, 네트워크 행위를 관찰하고 정책에 따라 제한한다.

목표는 이미 실행된 컨테이너가 예상과 다른 행동을 할 때 빠르게 알아채거나 막는 것이다.

### 3. 이미지·소프트웨어 구성요소 검사

- Trivy: 컨테이너 이미지, 파일시스템, IaC 설정과 시크릿 등을 검사할 수 있다.
- Syft: 이미지와 파일시스템에서 SBOM을 생성한다.
- Grype: 이미지·파일시스템·SBOM의 알려진 취약점을 검사한다.
- Clair: 컨테이너 이미지의 취약점을 정적으로 분석한다.

이 도구들은 알려진 취약점과 잘못된 설정을 찾는 데 도움을 주지만, 검사 통과가 이미지의 무조건적인 안전을 보장하지는 않는다. 출처, digest 고정, 서명, provenance 검증도 함께 필요하다.

### 4. 클러스터 설정과 컴플라이언스

- kube-bench: CIS Kubernetes Benchmark를 기준으로 클러스터 설정을 점검한다.
- Kubescape: 쿠버네티스 설정과 프레임워크 준수 상태를 검사한다.
- Popeye: 실행 중인 클러스터 리소스와 설정에서 잠재적인 문제를 찾아준다.

### 5. 승인 제어와 정책 강제

- Kyverno: 쿠버네티스 리소스 형식으로 검증·변경·생성 정책을 작성한다.
- OPA Gatekeeper: Rego 기반 정책을 Admission 단계에서 적용한다.

예를 들어 다음 요청을 배포 전에 거부할 수 있다.

- 특권 컨테이너 또는 root 실행
- 허용하지 않은 레지스트리의 이미지
- `latest` 태그 또는 digest가 고정되지 않은 이미지
- 필요한 보안 설정이 빠진 워크로드
- 조직 정책상 허용되지 않은 리소스

### 6. 네트워크 보안

- Cilium: eBPF 기반 네트워킹, 관찰성과 L3~L7 정책 기능을 제공한다.
- Calico: 쿠버네티스 NetworkPolicy 등을 이용해 워크로드 간 통신을 통제한다.

서비스 메시의 mTLS와 CNI의 네트워크 정책은 관련되지만 같은 기능은 아니다. 암호화, 인증, 통신 허용 범위를 구분해서 설계해야 한다.

## 국내 환경에서 살펴볼 제품·요구사항

- QueryPie KAC: 쿠버네티스 API 및 사용자 접근 통제, 명령·세션 감사 영역
- HIWARE for K8S: 쿠버네티스 계정·접근 통제 및 감사 영역
- Tatum CNAPP: 클라우드 보안 형상, 권한, 워크로드 보호와 컴플라이언스 영역
- AhnLab CPP: 클라우드 워크로드와 컨테이너 보호 영역

국내 환경에서는 기능 자체뿐 아니라 폐쇄망 설치, 오프라인 업데이트, ISMS-P·CSAP·금융권 요구사항 매핑, 한글 보고서, 기존 IAM·SIEM·CI/CD 연동 여부가 중요한 평가 기준이 된다.

## 제품 아이디어로 좁혀 보기

### 아이디어 A: CI/CD 보안 게이트웨이

여러 검사 도구를 하나의 판정으로 묶는다.

```text
커밋·PR
  → 이미지 및 의존성 취약점 검사
  → Dockerfile·Helm·Manifest 설정 검사
  → 시크릿 검사
  → 조직 정책 판정(Pass / Warn / Fail)
  → PR 피드백 및 빌드·배포 차단
```

핵심 차별화 후보는 다음과 같다.

- Jenkins, GitHub Actions, GitLab CI, Argo CD 등과 간단히 연동
- 결과와 차단 이유를 개발자가 이해하기 쉬운 한국어로 제공
- 승인된 레지스트리·베이스 이미지 등 사내 규칙을 YAML로 관리
- 폐쇄망에서 취약점 DB와 정책 팩을 안전하게 갱신
- 여러 도구의 중복 결과를 통합하고 우선순위를 제시

### 아이디어 B: 국내 규제용 Admission 정책 팩

Kyverno나 Gatekeeper 위에 국내 조직이 바로 적용할 수 있는 정책, 근거, 예외 관리와 증빙 기능을 제공한다.

- 특권 컨테이너 및 root 실행 금지
- 승인되지 않은 이미지 저장소 차단
- 보안 설정 누락 탐지
- 규제·내부 통제 항목과 정책의 매핑
- 예외 승인 이력과 준수 현황 대시보드

새 정책 엔진을 만드는 것보다 검증된 오픈소스 엔진에 정책 운영, 규제 매핑, 폐쇄망 배포와 사용자 경험을 더하는 접근이 현실적인 출발점이다.

## 스터디에서 이어갈 질문

1. 제품별로 빌드 전, 배포 전, 런타임 중 어디를 보호하는가?
2. 취약점 탐지와 악성 행위 탐지는 어떻게 다른가?
3. 탐지 결과가 틀렸을 때 예외를 누가 어떻게 승인하는가?
4. 폐쇄망에서 취약점 DB, 정책, 서명 키를 어떻게 갱신하는가?
5. 국내 규제 항목과 실제 기술 통제가 정확히 어떻게 연결되는가?

> 참고: 이 문서는 Canva 자료의 아이디어를 학습용으로 재구성한 것이다. 시장에 “제품이 없다”는 표현은 확정 사실이 아니라 추가 시장조사가 필요한 가설로 다룬다.
