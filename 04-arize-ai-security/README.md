# Arize AI와 AI 애플리케이션 보안

## 한눈에 보기

Arize AI 계열 플랫폼은 운영 중인 머신러닝·생성형 AI 애플리케이션을 관찰하고 평가하며 개선하는 AI 엔지니어링·옵저버빌리티 영역의 도구다. 핵심 흐름은 다음과 같이 정리할 수 있다.

```text
실행 추적(Trace) → 품질 평가(Evaluate) → 문제 분석 → 실험·개선(Learn) → 다시 운영
```

보안 제품과 완전히 같은 개념은 아니지만, 프롬프트 인젝션, 개인정보 노출, 환각, 위험한 도구 호출처럼 AI 애플리케이션에서 발생하는 위험을 관찰하고 평가하는 기반으로 활용할 수 있다.

## 주요 기능

### 1. 트레이싱

LLM 애플리케이션이 답을 생성하는 과정을 단계별로 기록한다.

```text
사용자 질문 → 검색 → 문서 선택 → 모델 호출 → 도구 호출 → 최종 답변
```

각 단계의 입력·출력, 지연 시간, 오류를 연결해서 보면 답변이 왜 느리거나 잘못됐는지 역추적하기 쉽다. 에이전트가 여러 도구를 호출할수록 이러한 실행 흐름 관찰이 중요해진다.

### 2. 데이터세트와 실험

실제 운영에서 발견한 문제 사례를 테스트 데이터세트로 만들고, 프롬프트·모델·검색 방식·에이전트 흐름을 바꿨을 때 결과가 나아지는지 반복 비교한다.

### 3. 프롬프트 플레이그라운드

코드를 매번 다시 배포하지 않고 프롬프트나 모델 설정을 바꿔 결과 차이를 빠르게 실험한다. 실험 결과는 직감이 아니라 동일한 데이터와 평가 기준으로 비교해야 한다.

### 4. 온·오프라인 평가

- 오프라인 평가: 배포 전에 준비된 테스트 데이터로 품질과 안전성을 검사한다.
- 온라인 평가: 실제 운영 중 생성된 트레이스와 응답을 계속 검사한다.
- 코드 기반 평가: 정답 일치, 형식, 금칙어처럼 명확한 규칙을 검사한다.
- LLM-as-a-Judge: 자연스러움이나 관련성처럼 단순 규칙으로 판단하기 어려운 항목을 다른 모델이 평가한다.

LLM 평가 결과도 오류와 편향이 있을 수 있으므로, 중요한 보안 판정은 사람의 검토와 결정적인 규칙을 함께 사용해야 한다.

### 5. 모니터링과 문제 사례 큐레이션

환각, 개인정보 노출, 품질 저하, 데이터 드리프트 등의 신호를 모니터링한다. 발견한 사례에 라벨과 설명을 붙여 재평가, 회귀 테스트, 프롬프트 개선에 다시 사용한다.

## AI 보안 관점의 네 가지 방어 지점

### 1. 모델 호출 전: 입력 방어

- 프롬프트 인젝션 의심 패턴 탐지
- 개인정보와 기밀정보 탐지·마스킹
- 입력 길이, 파일 형식, 출처와 권한 검증
- 사용자가 요청할 수 있는 작업 범위 제한

민감정보가 외부 모델로 전송된 뒤에는 되돌릴 수 없으므로, 전송 전에 검사하는 것이 중요하다. 단순 정규식만으로 모든 개인정보나 인젝션을 찾을 수는 없으므로 규칙, 분류 모델, 권한 검사를 조합해야 한다.

### 2. 모델 응답 후: 출력 방어

- 유해 콘텐츠와 정책 위반 검사
- 개인정보·시스템 프롬프트 노출 검사
- RAG 근거와 응답의 일치 여부 평가
- 답변의 인용, 형식, 허용 범위 검증

임베딩 유사도는 환각 판단에 도움이 되는 신호이지 완전한 증명은 아니다. 중요한 판단에는 출처 검증과 사람이 확인할 수 있는 근거가 필요하다.

### 3. 트레이스와 로그 저장소 보호

트레이스에는 프롬프트, 사용자 대화, 검색 문서, 도구 인자와 응답이 저장될 수 있다. 따라서 관찰 시스템 자체가 새로운 민감정보 저장소가 된다.

- 저장·전송 구간 암호화
- 최소 권한 RBAC
- 테넌트·프로젝트별 데이터 분리
- 보존 기간과 삭제 정책
- 수집 전 마스킹과 로그 필드 최소화
- 조회·내보내기 행위에 대한 감사 기록

### 4. 에이전트의 도구 호출 방어

에이전트가 이메일 발송, 결제, 파일 변경, DB 쓰기 같은 실제 작업을 수행한다면 텍스트 응답보다 피해가 커질 수 있다.

- 에이전트와 도구에 최소 권한 부여
- 허용된 도구와 인자 형식을 명시적으로 제한
- 위험 작업 전에 사용자 또는 담당자 승인
- 외부 콘텐츠를 명령이 아니라 신뢰할 수 없는 데이터로 취급
- 실행 환경 격리, 속도·비용 제한, 전체 감사 로그

## 공급망 보안과 연결되는 지점

AI 애플리케이션도 모델, 프롬프트, 데이터, 도구, 외부 패키지와 배포 파이프라인을 조합해 만든다. 따라서 전통적인 소프트웨어 공급망 통제와 AI 전용 통제를 함께 봐야 한다.

| 구성요소 | 확인할 질문 |
|---|---|
| 모델·API | 어떤 공급자의 어떤 모델 버전을 쓰는가? |
| 데이터·RAG 문서 | 출처와 변경 이력, 접근 권한을 확인할 수 있는가? |
| 프롬프트 | 누가 수정했고 어떤 평가를 통과했는가? |
| 도구·플러그인 | 무엇을 실행할 수 있고 권한은 어디까지인가? |
| 외부 패키지 | 버전, 취약점, 출처와 무결성을 검증했는가? |
| 배포 산출물 | 서명, SBOM, provenance와 승인 기록이 있는가? |
| 운영 트레이스 | 민감정보를 최소화하고 접근을 감사하는가? |

## 실습 아이디어

작은 LLM 애플리케이션 앞뒤에 보안 검사와 관찰 기능을 붙인다.

```text
사용자 입력
  → 입력 검사(개인정보·인젝션)
  → LLM/RAG/도구 실행
  → 출력 검사(근거·개인정보·정책)
  → 응답
          ↘ 트레이스·평가 결과 저장 → 대시보드
```

실습 결과는 탐지 성공 건수만 보지 않고 다음 지표로 평가한다.

- 탐지율과 미탐률
- 오탐률
- 정상 요청에 추가된 지연 시간
- 민감정보가 로그나 외부 API로 전송되기 전 차단됐는지
- 위험한 도구 호출이 승인 없이 실행되지 않았는지
- 프롬프트나 모델 변경 후 기존 안전성 테스트가 계속 통과하는지

## 핵심 결론

AI 옵저버빌리티는 “AI가 무엇을 했는지 보고 평가하는 기반”이고, 보안은 그 위에 명확한 정책, 최소 권한, 차단, 승인과 데이터 보호를 더해야 완성된다. 관찰만으로 공격을 자동 차단한다고 가정해서는 안 된다.

> 참고: Canva 자료에서 소개된 CloudNetworks는 국내 공급·파트너 맥락으로 언급되었으며, 제품 기능과 인증 범위는 도입 시점의 공식 문서로 다시 확인해야 한다.
